# New section

## 0. 요청서 확인

- 요청서 경로를 받았으면 읽는다. 채팅으로만 받았으면 `bash .my-harness/scripts/new-task.sh <slug>` 로 요청서를 만들고 들은 내용을 채운다.
- ★ 필수 항목(사이트 ID, 대상, Figma, 범위 밖, 완료 조건) 중 비었거나 "모름"인 것이 있으면 **구현 전에** 묻는다. 답은 요청서 "결정 · 질문 로그"에 적는다.
- 이후 단계마다 요청서의 "진행 기록" 체크박스를 갱신한다.

## 1. 근거 수집

1. 병원 정의서가 있으면 읽는다 (반응형·아이콘·공통 컴포넌트 적용 범위).
2. 팀 스킬 `platform-figma-fidelity` 의 절차대로 Figma 수치·이미지·코멘트를 확보한다. 그 지침이 정본이다.
3. 레이아웃이 "판단 맡김"이면 `docs/workflows/scale-to-fit.md` 기준으로 fluid / scale-to-fit 을 고르고 근거를 로그에 적는다.

## 2. 위치 결정

- 대상 앱에 이미 있는 폴더 구조·컴포넌트를 따른다.
- 🟡 앱에 기준이 없을 때 기본값:
  - 페이지: `app/<route>/page.tsx`
  - 섹션: `app/<route>/_components/<SectionName>.tsx` (그 페이지에서만 쓰는 경우)
  - 여러 페이지에서 쓰는 것: `components/<SectionName>.tsx`
- 공통 패키지 수정이 필요해 보이면 멈추고 묻는다.

## 3. 구현

- 재사용 우선: 앱의 `components/ui/` → 공통 패키지 → 새로 만들기.
- 섹션 하나에 한 컴포넌트. 300줄을 넘으면 하위 컴포넌트로 나눈다.
- 이미지·SVG 는 Figma 실제 에셋을 쓴다. 대체가 필요하면 로그에 적고 묻는다.
- 텍스트는 Figma 카피를 그대로 쓴다. 임의로 다듬지 않는다.

## 4. 검증 → 검수 → 보고

1. `verify` 스킬로 검증해 통과시킨다.
2. `design-reviewer` 서브에이전트에게 요청서 경로와 변경 파일 목록을 넘겨 검수받는다.
3. 지적 사항을 반영하거나, 반영하지 않은 이유를 로그에 적는다.
4. 요청서의 "확인하지 못한 것"을 채우고, 같은 내용으로 사용자에게 보고한다.
